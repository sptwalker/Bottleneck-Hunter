## 一、结论

**这 170 分钟不是算出来的，是等出来的。**

Phase 2（入围筛选）全长 **170 分 44 秒**（21:03:57 → 23:54:41），其中：

| 环节 | 耗时 | 占比 |
| --- | --- | --- |
| 供应商检索（28 个瓶颈环节 → 253 家候选） | **68 秒** | 0.7% |
| **Yahoo Finance 429 限流退避空转** | **168.5 分钟** | **98.9%** |
| 可投性过滤 + 落库 | 63 秒 | 0.6% |

空转段从 21:05:08 第一条 `Too Many Requests` 开始，到 23:53:38 结束，**338 次 429、中位间隔 30.0 秒**，`338 × 30 秒 ≈ 169 分钟`，与实测挂钟跨度 168.5 分钟吻合到 1% 以内——即整个扇出是严格串行的，且每条请求都在等一个被钉死在最大值的节流器。

没有任何一处超时保护、没有熔断、没有总预算。请求一次也没成功过，程序却坚持把 253 家公司一家一家问到底。

## 四、根因：三处叠加的缺陷

### 4.1 首要 · 函数叫 batch，跑起来却是串行

**位置：`bottleneck_hunter/chain/smart_money.py:312-334`**

```python
async def track_batch(suppliers):
    tasks = {s.ticker: (s, track_smart_money(s)) for s in suppliers}   # 一次性造出全部协程
    for ticker, (supplier, coro) in tasks.items():
        signal = await coro          # ← 逐个串行 await，并发度 = 1
```

字典推导式把 253 个协程全部造出来，紧接着用 `for` + `await` 一个一个等。所谓批量，实际吞吐等于 1，每个 ticker 都要独自承担完整的 30 秒节流惩罚。

同目录的 `financial_data.fetch_batch`（`financial_data.py:564`）**早已改成真并发**，还留着 `# 真并发：… （此前串行 await 使信号量形同虚设）` 的注释。smart_money 这条漏网了——同一类 bug 修了一半。

日志中的 `RuntimeWarning: coroutine 'track_smart_money' was never awaited` 正是这个写法的副产物。

### 4.2 放大 · 同一个 ticker 被两条独立链路各问一遍

**位置：`smart_money.py:179-265`、`financial_data.py:374-449`**

| 链路 | 每个 ticker 的 Yahoo 调用 |
| --- | --- |
| `_track_us_stock` | `stock.info`、`institutional_holders`、`insider_transactions`、`recommendations`（4 次） |
| `_fetch_us_financial` | `stock.info`、`quarterly_financials`、`history`（3 次） |

两条链共享同一个全局节流器、对**同一批公司**发问，`stock.info` 被读了两遍。

更关键：`throttle()` 每个 ticker 只调用一次，后续子请求**没有各自的节流**——只有整个包在 `try/except` 里失败时才 `observe(e)`。于是一个逻辑 ticker 实际消耗的 Yahoo 配额是它的数倍，而这些请求对总节流时间毫无贡献地溜了过去。

### 4.3 放大 · 失败即重试，且退避无上限、无终止条件

**位置：`smart_money.py:326-331`、`financial_data.py:573`**

两个 `*_batch` 都在失败后再整批重试一轮，请求量直接翻倍——而这些重试必然撞进同一个仍然 429 的窗口。

叠加 `yf_gate.observe()` 的规则（遇 429 间隔 ×2 退避、成功 ×0.9 缓慢回落），系统具备了一切「把 3 小时烧干净」的条件：一旦 429 成为常态，`_interval` 只会爬升到 `_MAX`（默认 30 秒）然后停在那里——这条路上没有任何成功可供衰减。**没有任何一处判断「今天拿不到数据了，该降级收手」，也没有任何超时预算。**

`yf_gate.py` 的设计意图本身是对的（先把「打得多快」压住，避免被 Yahoo 封），缺的是熔断与预算。

## 五、修复方案

按性价比排序。P0 是安全网，不改变任何业务语义；P1 是真正的提速；P2 是防止复发。

### P0-a · 给退避加熔断（3 小时 → 秒级失败）

**位置：`bottleneck_hunter/data_provider/yf_gate.py`**

在 `observe()` 里加连续失败计数器：

- 连续 N 次限流（建议 20）即置 `_tripped = True` 并记录时间；
- `throttle()` 见 `_tripped` 直接**快速失败**（抛 `RateLimited`），而不是 `sleep(30)`；
- 冷却 M 分钟（建议 15）后放行**一次**探测请求，成功即复位。

调用方捕获该异常后走「无数据」分支——这正是 `_fetch_us_financial` 里 `info = {}` 那条降级路径本来就能承受的结果。

同时给 Phase 2 的取数阶段加一个**总预算**（建议 5 分钟）：超时即停止扇出，用已拿到的数据继续评估。

> 取舍：宁可拿到 30 家的真实数据 + 明确的不完整标注，也不要 3 小时后拿到 85 家、且没人知道缺了什么。

### P0-b · 去掉失败后的整批重试（请求量 −50%）

**位置：`smart_money.py:326-331`、`financial_data.py:573`**

当前重试是在同一个 429 窗口里再跑一遍，必然全军覆没，只让请求量翻倍、把队列拖得更长。有了 P0-a 的熔断后重试意义本就不大；若保留，应改为**有上限的指数退避 + 抖动**，且仅在失败率低于某个比例时触发。

### P1-a · `track_batch` 改成真并发（并发度 1 → 4）

**位置：`bottleneck_hunter/chain/smart_money.py:312-334`**

```python
pairs = await asyncio.gather(
    *[track_smart_money(s) for s in suppliers], return_exceptions=True
)
for s, r in zip(suppliers, pairs):
    if isinstance(r, SmartMoneySignal):
        results[s.ticker] = r
    else:
        failed_suppliers.append(s)
```

语义与 `financial_data.fetch_batch` 完全对齐——该模块已经这么写并在生产运行，是现成的范式，直接照抄。并发上限沿用模块内已有的 `_SEMAPHORE = 4`（`smart_money.py:26`），不会把压力打爆。

### P1-b · 改用 Yahoo v7 批量行情（253 次 → 1 次）

**现成实现：`bottleneck_hunter/chain/supplier_search.py:170-240`**

项目里**已经有**一条批量取行情的通路 `_fetch_yahoo_quotes_relay()`，走借道 relay，一次 `/v7/finance/quote?symbols=A,B,C…` 就能取回全部候选的 `marketCap` / `trailingPE` / `exchange` / `quoteType`。其 docstring 明写：

> ③ `/v7/finance/quote?symbols=…` 批量单请求取全部候选（逗号分隔，天然规避逐调 429）

这正是 Phase 2 检索阶段只用 68 秒就拿到 253 家的原因。财务 / 聪明钱两条链完全应当复用同一条通路，而不是逐个 `yf.Ticker()` 去问。

需要 `.info` 之外的字段（机构持仓、内部人交易、季度财报）时，也应聚合成「按模块批量」的少量请求，并在**同一轮 Phase 2 内缓存 `.info` 结果**，让两条链共享，而不是各读一遍。

### P2 · 让「拿不到数据」可见（而非静默读秒）

- `85/253 成功，0 失败` 这行日志具有误导性——失败数恒为 0，前端和运维都看不出这一轮有 168 分钟在空转。应把因限流跳过的 ticker 计入 `failed_tickers` 并在 SSE 进度里显式提示。
- Phase 2 结束时若限流占比超过阈值，在结果页标注「本轮美股财务/聪明钱数据不完整」。
- 顺带：同时段还有 `用户 xxx 无可用 LLM，冻结其定时自动化`、`IMAP 认证/账户异常` 等无关噪声在刷日志。它们不影响本次耗时，但排查时会淹没真正的信号，值得单独收敛。

## 七、实施结果（2026-09 复盘后落地）

方案已全部实施。这里记录**实测数字**与两处方案外的补充发现——都是量测之后才看清的。

### 7.1 一个把「熔断就够」证伪的测量

只按次数熔断（连续 20 次 429）在纸上看着够快，实测不是：在生产默认参数下（`MIN=3s`
`MAX=30s`、253 家候选、两条链全 429），从冷启动到熔断后收尾全程耗时 **537 秒**，其中**熔断
本身就是等到第 327 秒才触发的**——`YF_TRIP_WINDOW` 这道新口径要解决的正是这 327 秒。

原因是退避是**翻倍**的：3→6→12→24→30，第 20 次连续 429 到来时，间隔早已顶到 30s 上限，
前面 19 次累计已睡掉约 5 分钟。**阈值定得越高，白等越久**——按次数熔断的等待时间与阈值线性
相关，这跟「加熔断是为了快」的初衷相反。

因此 `yf_gate` 的熔断加了第二个口径：连续限流**持续** `YF_TRIP_WINDOW`（默认 90s）即熔断，
与次数满足其一即可。这样无论失败来得快还是慢，最坏等待都由窗口封顶，而不是由
「阈值 × 退避倍数」决定。任何一次成功（含冷却后的探测成功）清空计数并重开窗口，所以不会拿
几分钟前的旧限流误熔断当前这一轮。

> 顺带纠正一处此前的口误：早前汇报过的「该场景 8.38 秒收敛」是错的。那个数字来自一个把
> `YF_MIN_INTERVAL` 压到 0.05s 的测试档，不是生产曲线。生产默认下的真实数字是上面这 537 秒。

### 7.1.1 根因不是「没熔断」，是闸门在**排队**

加上 `YF_TRIP_WINDOW` 后 `--prod` 仍稳定停在 **297.01s**，熔断器还是没跳（连续计数只有 3）。
这不像「差一次收尾睡眠」的边界问题，于是把每次进闸都打成日志量了一遍，看清了真正的原因：

**`_next_at` 不是「上次调用时间」，而是一条向前的预约队列。** 每个调用者进来先把槽位往后推
一格（`_next_at = start + _interval`），于是**第 N 个并发者要等的是 N × `_interval`**，而这个
深度**不受 `_MAX` 约束**——`_MAX` 只封顶「单个间隔」。实测：起跑瞬间 **9 个并发者同时进闸**，
依次排到 3s / 9s / … / 45s；到 t=63s 时进门的那次已被排到 **234s 之外**。

后果是三重的，且互为因果：

1. 失败被推到队尾才发生（t=27s 的日志写着「取数预算已用尽（余 183.0s，需等 210.0s）」）；
2. 熔断器的**连续计数永远涨不上去**——2026-09 那轮 253 次 429 里只累计到 3，因为排名靠前的
   调用还在睡，还没轮到它们失败；
3. 于是 300s 的取数预算被拖穿成 297s，且熔断始终不触发。

**这不是「错峰」，是积压。** 修法是把队列按本轮节拍封顶：

```python
_next_at = min(_next_at, now + _interval)   # 一个间隔内只放行一个槽
if left is not None:
    _next_at = min(_next_at, now + left)    # 再按剩余预算收敛
...
if left is not None and wait >= left:
    raise RateLimited(...)                  # 睡不起就不睡，立刻降级
```

代价是并发被削到与节拍一致——这正是「**限速不是限并发**」的本意：Yahoo 管的是调用**频次**
不是同时几个在飞，多出来的并发本来就拿不到数据源，早点走「无数据」降级分支，比睡在队里对
上层更有用。修完 `--prod` 从 297.01s 落到 **84.03s**，熔断于 66.03s，连续计数 506（不再卡在 3）。

### 7.2 实测对照

| 档位 | 参数 | 耗时 | 熔断于 | 结果 |
| --- | --- | --- | --- | --- |
| 修复前（现状） | 生产默认 | **10110 s**（168.5 min） | 无熔断 | `85/253 成功, 0 失败` |
| 仅次数熔断 | 生产默认 | **537 s** | 327 s | 睡眠仍占满 5 分钟 |
| 次数 + 持续时间 | 生产默认 | **297 s** | 未触发 | 预算被队列拖穿，计数卡在 3 |
| **+ 队列封顶（现行）** | **生产默认** | **84.03 s** | **66.03 s** | `0/253 成功, 253 失败`，计数 506 |
| + 队列封顶（现行） | 快档（间隔压到 0.05s） | **11.02 s** | 2.33 s | `0/253 成功, 253 失败` |

复现脚本 `scripts/repro_phase2_429.py` 可重跑两条曲线：默认档测逻辑（秒级），`--prod` 测
真实最坏等待。断言包含「两链各失败 253」与「降级计数 ≥ 253」，即失败必须可见，不能重现
「0 失败」。两档均 `EXIT=0`。

> 「84 秒」这个数字里，66 秒是**熔断真正生效前的必要观测**（93 次真实 429 打满 90s 窗口），
> 剩下 18 秒是熔断跳闸后 253 家走完降级分支的开销。想再压只能动 `YF_TRIP_WINDOW`，而那是在
> 「更快收敛」与「别把偶发限流误判成封禁」之间取舍，不是纯优化。

### 7.3 方案外的补充发现：失败被伪装成成功

诊断阶段只看到「0 失败」这行日志可疑，落地时定位到了根因，这比原方案的 P2（把失败显示出来）
更靠前一层：

- `financial_data._fetch_us_financial` 的外层 `except` 兜住 429 后，返回一个**全 None 的
  `FinancialSnapshot`**，`data_source='yfinance'`；
- `smart_money._track_us_stock` 同样返回**中性壳** `SmartMoneySignal(smart_money_score=5.0)`。

两者在下游都与「真的取到了、只是字段为空」不可区分，于是批量层只能记成成功——这才是
`85/253 成功, 0 失败` 的字面来源，也意味着**缺失数据以 5.0 分的形式参与了评分**。
现已改为：一次都没取到即返回 `None`，交给批量层计入 `failed_tickers`。
两处对应的单元测试原本断言的正是旧的空壳语义，已一并改掉（原断言本身就是这个缺陷的固化）。

### 7.4 各项落地位置

| 项 | 位置 | 说明 |
| --- | --- | --- |
| P0-a 熔断 | `data_provider/yf_gate.py` | 次数 **或** 持续时间任一满足即熔断；冷却后放行一次探测 |
| P0-a 队列封顶 | `data_provider/yf_gate.py::throttle` | `_next_at` 按本轮节拍封顶，并发者不再被排到 N × 间隔之外（见 §7.1.1） |
| P0-a 总预算 | `chain/fetch_budget.py`（新） | 默认 300s，协作式：取数前查预算，到点**正常返回已得部分** |
| P0-b 去整批重试 | `smart_money.py` / `financial_data.py` | 重试改为受预算与熔断约束，不再在同一个 429 窗口里翻倍 |
| P1-a 真并发 | `smart_money.py::track_batch` | `asyncio.gather` + `_SEMAPHORE = 4`，与 `fetch_batch` 同范式 |
| P1-b 聚合并共享 `.info` | `chain/quotes_cache.py`（新） | 轮内共享缓存：同一只票财务链与聪明钱链只打一次 |
| P2 失败可见 | `web/streaming/phases.py` + 前端 | 失败计入 `failed_tickers`；降级比 >30% 时结果页显红条标注 |

> 为什么总预算用协作式而不是 `asyncio.wait_for`：`wait_for` 取消的是外层 `await`，
> `gather` 会连**已经取到的结果一起丢掉**，而且它也杀不掉已经阻塞在
> `asyncio.to_thread` worker 里的 `time.sleep`。取数是「有则更好」的增强环节，正确的语义是
> 「到点就不再发起新的，已到手的照常评估」。
